Отчёт: почему dao.ts (голосование по весам гейджей) нельзя пока перевести
с api.curve.finance/getAllGauges на prices.curve.finance/v1/dao/gauges/overview
================================================================================

Дата: 2026-07-21
Где используется старый эндпоинт: src/dao.ts, функции getVotingGaugeList() и
userGaugeVotes(). Обе тянут _getAllGauges() из src/external-api.ts
(https://api.curve.finance/api/getAllGauges).

ВЫВОД КОРОТКО
-------------
Переносить голосовалку на новый эндпоинт пока нельзя. Нашлись две блокирующие
проблемы:

  1) Нет root-гейджа для L2-гейджей — новый API отдаёт effective_address,
     но это НЕ то же самое, что legacy-поле rootGauge. Без него голоса за
     L2-пулы будут читаться с неправильного адреса и просто не найдутся.

  2) gauge_relative_weight в новом API отличается от legacy РОВНО в 100 раз
     (единицы измерения разные). Если взять значение как есть — все проценты
     веса гейджей будут в 100 раз меньше реальных.

Плюс не хватает вспомогательных полей (hasNoCrv), но это уже не блокер, а
мелкая доработка.


ПРОБЛЕМА 1: root-гейдж для L2 (голосование сломается для L2-пулов)
--------------------------------------------------------------------
Как это работает сейчас (src/dao.ts, userGaugeVotes):

    const gaugeData = Object.values(await _getAllGauges());
    for (const d of gaugeData) {
        const gaugeAddress = d.rootGauge ? d.rootGauge : d.gauge;
        calls.push(gcMulticallContract.vote_user_slopes(address, gaugeAddress));
    }

Контракт GaugeController живёт только на mainnet. Для гейджа, задеплоенного
на L2 (Polygon/Optimism/Arbitrum/...), в GaugeController зарегистрирован не
сам L2-гейдж, а его "зеркало" на mainnet — root-гейдж (root_gauge_factory).
Голосовать/проверять голоса нужно именно по адресу root-гейджа, иначе
vote_user_slopes() вернёт пустоту (гейдж просто не найден в контроллере).

Legacy API отдаёт это прямо полем rootGauge. У нового API есть поле
effective_address — по названию похоже на кандидата на замену, но фактически
это НЕ root-гейдж. Проверил на живых данных:

  Взял 6 L2-гейджей (Polygon) с прошлого сохранённого дампа
  api.curve.finance/getAllGauges, у которых rootGauge явно отличается от
  локального адреса гейджа, и посмотрел на эти же адреса в новом API:

    gauge (локальный, L2)                       legacy rootGauge (mainnet)                   effective_address (новый API)
    0x9392abf3bf0a8446f4b93c9af72429ff5d157021   0xb737dca332602937c9090203577d714c377773a0   0x9392abf3bf0a8446f4b93c9af72429ff5d157021  (= локальный, НЕ root)
    0x453d025c712eade027c7d6dfd6bb5269a3319b23   0x7156e1d43273f4a9821487ae658bd8f70e5c6eed   0x453d025c712eade027c7d6dfd6bb5269a3319b23  (= локальный, НЕ root)

    0x1b265bcd37b80a940660e209832b68bfa7a7bb82   0x18904ac503a1b26476313738a6221be7be5083be   0x1b265bcd37b80a940660e209832b68bfa7a7bb82  (= локальный, НЕ root)

  На всех 6 примерах effective_address совпадает с локальным (L2) адресом
  гейджа и НЕ совпадает с rootGauge из legacy API. То есть effective_address —
  какая-то другая сущность (возможно, адрес для расчёта APR/буста), не то,
  что нужно для голосования.

  Отдельно проверил на Optimism: из 30 гейджей у 29 address === effective_address
  (то есть для большинства это вообще всегда одно и то же значение, разница
  всплывает только в паре особых случаев вроде gauge для Savings crvUSD).

Чем это грозит, если просто взять gauge.address из нового API вместо rootGauge:
  vote_user_slopes(user, L2-адрес-гейджа) на mainnet GaugeController вернёт
  нулевые голоса (гейдж с таким адресом там не зарегистрирован). Строка
  "if (votes[i][1] === BigInt(0)) continue;" в userGaugeVotes() эту запись
  просто выкинет из результата — реальные голоса пользователя за L2-пулы
  молча исчезнут из ответа userGaugeVotes(). Для getVotingGaugeList() будет
  похожая история с весами.


ПРОБЛЕМА 2: единицы измерения gauge_relative_weight отличаются в 100 раз
--------------------------------------------------------------------------
Legacy API отдаёт голые ончейн-значения (wei-масштаб), которые в коде
форматируются через formatUnits:

    totalVeCrv: this.formatUnits(gaugeData[i].gauge_controller.get_gauge_weight, 18),
    relativeWeight: this.formatUnits(gaugeData[i].gauge_controller.gauge_relative_weight, 16),

Новый API отдаёт уже готовые числа с плавающей точкой (gauge_weight,
gauge_relative_weight) — но масштаб другой. Сравнил один и тот же гейдж
(0x7ca5b0a2910b33e9759dc7ddb0413949071d7575, "cDAI+cUSDC") на конкретный
момент времени:

    legacy raw gauge_relative_weight = 2667315107511
    legacy formatUnits(x, 16)        = 0.0002667315107511   (это то, что сейчас
                                                              попадает в поле
                                                              relativeWeight)
    новый API gauge_relative_weight  = 0.0000026673151075110003

    0.0002667315107511 / 0.0000026673151075110003 = 100.0  ровно

Итого: значение из нового API нужно домножать на 100, чтобы получить то же
самое число, что сейчас видит пользователь в relativeWeight/totalVeCrv. Если
подключить новый API "как есть" без этой поправки — все проценты весов будут
в 100 раз заниженные.

(Похоже на то, что legacy отдаёт "проценты" (100 = 100%), а новый API —
"долю" (1.0 = 100%). Нужно подтвердить у бэкенда, что это действительно
так везде и не единичный случай.)


ЧТО ЕЩЁ ОТСУТСТВУЕТ (не блокер, но на заметку)
------------------------------------------------
  - hasNoCrv — используется в getVotingGaugeList() как часть условия
    пропуска гейджа ((is_killed || hasNoCrv) && relative_weight === 0). В
    новом API такого поля нет. Без него часть "полностью мёртвых, без CRV"
    гейджей может остаться в списке голосования, хотя раньше пропускалась.
  - poolUrls / shortName / blockchainId — это чисто отображаемые поля
    (ссылка на пул, короткое имя, имя сети), их несложно восстановить из
    pool.chain / pool.name нового API, тут проблем не вижу.


ЧТО НУЖНО ОТ БЭКЕНДА, ЧТОБЫ ЗАКРЫТЬ МИГРАЦИЮ
------------------------------------------------
  1. Поле-эквивалент rootGauge (адрес зеркального root-гейджа на mainnet
     для L2-гейджей) — без него голосование за L2-пулы нельзя мигрировать.
  2. Подтверждение масштаба gauge_weight / gauge_relative_weight (правда ли
     везде разница ровно в 100 раз, или это частный случай).
  3. (Опционально) hasNoCrv или его аналог.
  4. (Отдельная тема, см. предыдущий отчёт по gauge.address) — gaugeStatus
     ({areCrvRewardsStuckInBridge, rewardsNeedNudging}), нужен для
     pool.gaugeStatus(), сейчас live и не мёртвый (rewardsNeedNudging=true
     сейчас у 3 гейджей).

До получения этих полей src/dao.ts трогать не стоит — это голосование
реальным veCRV, ошибка в адресе гейджа или единицах измерения — это не
косметика, а искажение данных о голосах пользователей.
